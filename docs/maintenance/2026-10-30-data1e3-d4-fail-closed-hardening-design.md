## 2. Non-negotiable behavior before proposed implementation

1. **Never overwrite** current existing \`flights\` / \`fstd_sessions\` on replay, stale-plan conflict or cross-user/global-ID collision; protect their full certification/locking fields, archived R1/R2, verification and voided history. Missing/ambiguous source IDs are errors, not generic identity fallback.
2. **Stale preview != approval to write.** Preflight classification may provide user guidance, but final restore must validate data state within the write transaction; an existing identity created between preflight and commit must result in a rollback/fail-closed conflict. No \`ON CONFLICT DO NOTHING\` followed by \`UPDATE\` from unverified planned IDs.
3. **Preserve all independent audit events.** Deletion by \`id > maxAuditReadBeforeTransaction\` and \`flight_id\` is forbidden. An audit row's increasing ID is not provenance or a safe authorization to delete it. Do not alter unrelated append-only history; do not suppress new certification/void audit triggers globally.
4. **Accurate committed result.** If successful, report inserted rows actually committed (per section, not planned \`preview.add\`). If write fails/aborts, return no invented added counts. Pre-restore safety backup persists separately and must be described as a legitimate non-atomic safety side effect.
5. **Version and account trust unchanged:** require verified stored-v13 HMAC from #445, keep supported legacy handling and existing account/certification checks; no silent migration of old signed archives or downgrade to unsigned. Preserve exact monetary v21 provenance, full source/voided flight relationship rules, shared participant evidence and natural keys.
6. **No new database schema/library by default.** Existing Neon HTTP \`sql.transaction(queries)\` accepts a fixed array of query promises and returns ordered per-query row arrays; the local PostgreSQL adapter defers and later executes those statements in a transaction. The design must work on **both** without assuming mutable in-flight query orchestration, dynamic SAVEPOINTs or an unapproved new database connection/pool.

## 3. Recommended minimal mitigation (Option A — fail closed first)

**A1 — flight and FSTD identity conflict is an atomic error.** For precisely \`plan.addRows.flights\` and \`plan.addRows.fstd_sessions\`, remove the silent conflict swallowing \`ON CONFLICT DO NOTHING\` from staging INSERTs; any primary-key/unique conflict raises an error **inside** the existing main \`sql.transaction(queries)\` and aborts the transaction **before** the certification UPDATE can commit. Include an explicit suitable safe public \`AccountRestoreConflictError\` / generic catch conversion; never return raw SQL, connection, internal row data or credentials to the user. For idempotent already-present rows identified at fresh preflight, \`plan.addRows\` excludes them and they are not updated. This is preferable to silently updating or silently skipping a new conflicting identity. **Review carefully** whether an additional guard is needed for cross-user key collisions and preexisting/voided evidence; fail closed on all ambiguity.

**A2 — protect existing audit append-only data.** Remove current broad line-266 deletion based on global \`MAX(flight_audit_log.id)\` and planned flight IDs. Preserve generated audit records by default and insert recovered archived audit events with the existing duplicate-ID safety guard where policy permits. **Unresolved semantic question:** the staging INSERT and certification UPDATE may generate transient audit events via triggers; preserving them can change event counts and provenance. Before implementing A2, inventory actual triggers and audit semantics at canonical schema v21; if transient events truly must be deduplicated, design a mechanism bounded to **rows conclusively created by the very same restore transaction** and subject it to independent review/tests. Do not substitute \`xmin\`, txid thresholds, blanket trigger disable or a different broad delete without explicit provenance validation.

**A3 — exact actual inserts, not preview counts.** Under \`sql.transaction(queries)\`, add \`RETURNING\` to bounded INSERT statements and track the query's associated section, then sum the actual returned rows for successful commit. Review all sections and batch sizes rather than fixing only flights/FSTD; other \`ON CONFLICT DO NOTHING\` calls can also cause \`preview.add\` overcounts. On new/legacy protected tables where INSERTs lack \`RETURNING\`, make deliberate idempotency/counter contracts, including optional settings/profile updates and existing rows, and respect \`EXACT_RESTORE_STATEMENT_LIMIT\`. If Neon HTTP/local adapter returns different shapes or large \`RETURNING\` payloads, return only bounded counts using SQL \`WITH inserted AS (... RETURNING 1) SELECT COUNT(*)\` **after verifying** both adapters' row-producing detection; avoid returning full GPS or certification content. Successful result should reflect actual committed changes; failed transaction reports no successes.

**A4 — final state and replay.** Because \`prepareExactAccountRestore()\` observes data before the main write, the follow-up MUST use execution-time fail-closed INSERT/constraints for conflicts, and consider explicit bounded assert/revalidation inside the transaction for protected revisions, voided tombstones, provenance and owner-scoped record identities. A SELECT before the INSERT alone is race-vulnerable. Avoid arbitrary per-user advisory locks as the only guarantee: other writers might not acquire them. Keep exact account scoping for each table, and ensure no mutation to an existing protected record if any stale identity emerges. Verify source-versus-row classification across all backup sections, not just flight/FSTD.

**A5 — transaction and safety-backup boundary.** Main restore SQL is one transaction; any mid-way unsafe conflict must roll it back. \`createStoredBackup(userId,"pre_restore")\` runs before the main restore transaction and may remain if the restore then fails. The UI must not claim zero writes across the entire attempt; it must distinguish \`main restore aborted\` and \`safety backup retained\`. Authorization and HMAC checks must precede both preview and new safety-backup write.

## 4. Alternative and explicit trade-off (Option B)

**Option B — inserted-row-only updates via transaction-owned IDs.** Keep conflict-tolerant staged INSERT, but derive the set of actual successful inserted IDs from \`INSERT ... RETURNING id\` *inside the same transaction*, and allow certification UPDATE/child inserts/audit cleanup only for that exact set; if a planned ID is absent from returned IDs, choose an explicit abort rather than silent success for any protected flight/FSTD. Requires safe statement/result coupling across Neon HTTP and the local adapter without dynamic query creation midtransaction; may require a CTE, temp table or single bounded SQL statement. More complex and easier to get wrong than Option A. **Do not implement** without reviewer verifying SQL syntax, transaction boundaries, statement budget, trigger behavior, and full legacy/protected child relationships.

**Recommended order:** freeze and review Option A **before runtime edit**, because failing closed on a concurrent collision has the smallest semantics surface. Keep A2 audit-trigger provenance and A3 counters as explicit blocking sub-decisions until verified; do not claim D4 complete by only removing two \`ON CONFLICT DO NOTHING\` phrases.

## 6. Design-time verification / unresolved questions

- **Q1:** Which current \`flights\`/FSTD triggers fire on staged INSERT and certification UPDATE, and exactly which audit rows are legitimate immutable history? Is removing audit cleanup compatible with user-visible audit and certified event chains? 
- **Q2:** Are all new flight/FSTD IDs from a signed v13 source unique across account and backed by explicit source-account validation? Confirm other natural-key/existing voided-history conflicts between preview and commit.
- **Q3:** Can \`sql.transaction(queries)\` return bounded per-statement inserted counts consistently in both Neon HTTP and \`lib/local-postgres.ts\`, without changing the snapshot/read-only adapter? What if \`RETURNING\` increases output beyond the local 16MiB buffer?
- **Q4:** What error contract should show on a DB uniqueness collision versus a preflight \`AccountRestoreConflictError\`, and how to prevent raw errors/existence leaks? 
- **Q5:** Is Option A strict unique-conflict rollback sufficient for mutable or authenticated child sections not protected by the parent ID; do they require separate guards? 
- **Q6:** How will *true simultaneous* two-session races be orchestrated in one physically verified disposable PG16 with trigger/transaction semantics, and how will successful owned-cluster cleanup be evidenced? 
- **Q7:** What is the safest minimal implementation split: A1 core overwrite prevention, A2 append-only audit, A3 counts, A4 full protected ID assertions; which tests must precede each split?
- **Q8:** Source-review the pre-restore safety backup boundary and schema ensure path: outside the SQL transaction, legitimately persistent vs forbidden writes. 
- **Q9:** Check compatibility with canonical \`sql/\` migrations/v21, private account data, voided certified history, participant evidence and shared pilots without inventing data. Reconcile schema/constraint/trigger evidence before first patch.
- **Q10:** Determine whether a wider design (all protected child tables) is necessary. If so, recommend a separate roadmap milestone; do not silently broaden this minimal D4 patch.
