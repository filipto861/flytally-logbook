## 2. Critical design gap: physical clone identity is not authenticated by an installation UUID

A database clone can copy a proposed `source_instance_id`, existing local `flight_audit_log.id`, rows, and server signing material. Therefore **(installation ID, native BIGSERIAL ID)** is not sufficient to prove unique *post-clone* events. A legitimate later native event in each clone could have the same numeric ID. The installation ID is a **lineage claim**, not a physical machine or uninterrupted history attestation.

**N1 — native table untouched (lower initial migration blast radius):** all pre-v14 native rows remain snapshot-scoped evidence on external imports; cross-snapshot overlaps without proof fail closed (like v13 A), including ordinary later v14 exports. This remains safe but does **not** solve normal incremental backup deduplication for imported native event history.

**N2 — recommended for meaningful v14 recovery (new owner decision required):** introduce an **additive, immutable native event UID**, assigned once per native audit row when first recorded, e.g. an independently random UUID with DB-generated default. Keep original native `BIGSERIAL id`, trigger action semantics and other columns intact. A source-authenticated v14 native row includes `event_uid`, `native_source_id`, source account, full event payload digest and an honest assignment-provenance tag.

*Why N2:* if two cloned DBs share an event already assigned an UID, shared history retains the same token; if they independently append a new event after cloning, each insertion receives a newly generated unpredictable UID instead of assuming coincident numeric `BIGSERIAL` means one event. **This is a probabilistic identity scheme with operational assumptions**, not independent physical origin attestation, and cannot prevent malicious copies/reassignment. An adversarial/invalid duplicate UID with different bytes must reject; same UID with same bytes can only be treated as equal *under an explicitly authenticated lineage + source policy*. Do not infer user action or regulatory evidence from UID.

**Pre-v22 native history/backfill constraint:** existing native audit rows cannot retroactively prove an event UID at original creation. If N2 is approved, introduce nullable UID first and an authorized, resumable, **explicitly labelled migration-time assignment** for existing rows. This does not change source `id/action/old/new/changed_at`; assignment time and version are separately recorded. Historical rows already diverged across clones before assigning UIDs **cannot** safely deduplicate just because content matches. Migration requires strong verification, no overwriting existing non-null UID, account-scoped indexes/uniqueness and no remote DB mutation without distinct owner approval. `gen_random_uuid()` or equivalent generator availability and exact DDL/lock/performance on local PG16 must be verified, not assumed. Never use literal 0/unknown as invented UID.

**Important compatibility:** the current v13 `SELECT * FROM flight_audit_log` and v6 restore `json_populate_record(NULL::flight_audit_log,...)` are schema-sensitive. Adding a native UID can change exported v13 row shape and legacy INSERT semantics. A migration approval must be conditioned on proving signed-v13 backward compatibility and safely blocking unsafe F9. A column with a default alone is **not** evidence that the current v13 restore is compatible.

## 3. Candidate v14 signed payload contract

Keep `format="pilot-logbook-portable"`; set `version=14` only when full validation is active. Do **not** alter existing v13 backup payloads/signatures. `schema_version` is an independent database migration status, not the backup format version.

| v14 field or section | Meaning | Required / fail-closed rule |
| --- | --- | --- |
| `audit_log` | **Native** database trigger `flight_audit_log` rows only, with local audit IDs and **proposed** native event UID+UID origin status if N2 is approved | Required array, including empty. Never include imported ledger rows here. Per-row source account and UID status validated. |
| `imported_audit_events` | Account-owned immutable imported ledger rows, original `source_user_id`, `source_audit_id`, `source_flight_id`, original event claim, signed snapshot origin and original digest, canonical event content fingerprint, proof/authenticity tier and import operation | Required array including empty. Original v13 digest and snapshot namespace **survive v14 re-export unchanged**; do not rewrap v13 source claims as native v14 claims. |
| `imported_event_flight_links` | L1 has **no** verified links, but define an explicit required **empty** array and count=0 to reserve a strict future L2 contract; in L1 a nonempty array MUST reject as unsupported, not silently discard | Required, exactly `[]` at L1 first release. Any future link format requires deliberate upgrade/version/effectivity decision. |
| `origin_lineage` | Signed account/installation **claim** metadata: logical installation identifier if adopted, lineage/epoch identifier, generator version, event UID scheme and post-clone limitations | Required strict object (or explicit one-row section) with clear "declared/derived" labels; never promote a copied UUID to independent proof. Absent/unknown fields cannot default to approved origin. |
| `audit_provenance_version` | Version of the complete provenance field schema, separate from `version=14` | Must equal explicitly supported version, not any positive integer. |
| `event_fingerprint_version`, `event_digest_algorithm` | Domain-separated exact comparison algorithm and version; distinguish JSON lexical fidelity from semantically normalized fields | Explicit, fixed test vectors and number/timestamp/null handling; unsupported versions reject. |
| `counts` | Exact existing v13 section counts **plus** `imported_audit_events` and `imported_event_flight_links` | Required every-array count; mismatch or unknown mandatory section rejects; no silent `[]` normalization for omitted v14 arrays. |
| `integrity` | Version-bound authenticated payload digest and server signature; sourceUserId plus complete included provenance data | Signature verified using exact version-specific payload contract; do not blindly accept v13 `>=13` dispatcher for v14. Include signature key version/id under rotation policy. |

**Crucial authenticity distinction:** v14 signed whole payload authenticates all included fields **when the entire file is present and successfully verified**. It does not automatically provide a stand-alone cryptographic *membership proof* for one exported row after its original signed file is discarded. Each restored imported row must honestly preserve a tier such as `snapshot_signature_verified_at_import` vs `independently_reverifiable_event_membership` (the latter **unavailable** until source file or valid inclusion proof/certificate is retained). A receipt signed by the importer is proof of the importer's *attestation*, not third-party source history. No implicit certification/regulatory status.

**Canonical source format:** preserve `source_version`, original source digest, source event ID/text fields and immutable account actor claim. Store `original_event_jsonb` and a **versioned canonical event representation/hash**. Never call raw JSON bytes in a v13 file “directly signed source event bytes”: currently v13 signs the serialized parsed whole payload. Comparison must specify integer precision, timezone, missing vs null, duplicate keys, canonical key ordering, and forward/backward JSON compatibility; ambiguous lexical input fails closed. This is a design requirement, not a claimed existing algorithm.

## 4. Evidence retention: minimal privacy-preserving default for owner decision

Two implementable alternatives, neither automatically approved:

- **R1 — recommended first milestone:** retain the original immutable event fields already represented by `original_event_jsonb`, the server-computed deterministic canonical event hash+version, verified original signed backup digest/source user, authenticity tier, import operation and **audit of import-time signature validation**. Do **not** duplicate the entire signed source backup or additional unbounded raw JSON event bytes by default. Label membership **“verified against signed source snapshot at import”** only; later standalone re-verification of source membership remains UNAVAILABLE if the source file is gone. This contains duplication and sensitive data, while being honest about proof limits. It requires bounded row/array size and key-rotation lifecycle.
- **R2 — stronger standalone proof, larger scope:** retain original signed payload under an explicit privacy/storage policy, **or** define a version-specific signed per-event commitment/Merkle root with durable inclusion proofs and key history. R2 allows independently rechecking membership when all necessary proof material is present, but increases payload sizes, key management, DB migration/retention, privacy erasure and attack surface; needs independent reviewer and explicit owner scope.

**Recommendation:** use R1 in L1 first release **only if owner accepts the deliberately limited later membership claim**, while keeping strict file verification at import and immutable source evidence. A true archival/regulatory proof should not be advertised on R1 alone. No secrets, raw private flight/GPS records or complete signed backup blobs in Git, tests, errors or documentation.

**Existing stored backups:** `lib/backup-center.ts:13-26` automatically prunes older stored backups by retention policy, including automatic/manual/`pre_restore`; this means *real* retention is an executable code contract. The owner uses a single-user installation but no account-backup table inventory was inspected. v14 must define retention and restore availability explicitly; silent prior-backup deletion or data-loss downgrade is never authorized by L1/v13 A. A new retention policy is **separate owner consent** if changed.

## 5. Complete snapshot, presign and all-path readback — release barrier

The existing v13 builder `lib/account-backup.ts:22-56` issues **32 ordered queries** (2 transaction-state probes + 30 account-data sections) under one read-only REPEATABLE READ transaction. `lib/account-backup-snapshot.ts:51-68` hard-codes 32/section index; `lib/account-backup-presign.ts:36-39` only allows v13; `lib/portable-backup.ts:133-143` treats unknown >=13 as v13. This is confirmed old executable, not v14 readiness.

**Candidate v14 L1 exact section manifest**: retain all 30 current account-data SELECTs, add `imported_audit_events`, required empty `imported_event_flight_links` through a strict consistency assertion, and `origin_lineage` record from the proposed versioned schema. If each is a separate SELECT, **candidate query result count = 35** (two probes + 33 selections). If a fixed literal empty link section is built without SELECT instead, **a distinct manifest and probe count must be frozen and reviewed**; never silently claim 35 for a different query array. This count is a design illustration, **not a tested query budget**.

All v14 backup creations must:
1. Positively detect expected schema shape, migration/permission flags and supported signer key; fail before signing if any unavailable.
2. Collect native audit + imported evidence + account profile + origin claims + complete existing sections in **one MVCC snapshot**; use versioned position manifest and correct first/last matching snapshot probes, exact tenant scope, sorted result order. Do not substitute independently scheduled reads.
3. Validate exact arrays, counts, owner/cross-party relationships, certified/voided records, money provenance and every imported row's source authenticity/provenance, duplicate IDs and canonical fingerprints **before** signing. No broad try/catch that turns invalid source into success or truncated data.
4. Calculate the entire v14 signed payload digest, signature, version/issuer policy; only then serialize a complete file. After storage, read/decompress/parse/verify full payload before treating a backup as recoverable.
5. Cover **download/export**, stored **automatic**, **manual**, and **pre_restore**, including retention, size limits, backup listing, migration compatibility and verified readback. `pre_restore` is separately committed; it must be complete and survive a rolled-back main restore.
6. **Feature-off and rollback:** once any imported ledger row exists, reverting backup writer to v13 would create a signed incomplete backup. The v14 complete writer stays available even if imported write feature is OFF; if schema/backup writer is unavailable, backups and restore must **FAIL CLOSED**, with explicit user-facing unavailable state. No old F9 restore route on unsupported version/schema/flag; stage rollout so full v14 backup handling is verified **before** enabling any imported ledger writes. A failed automatic backup must not be called success and restore must not proceed after failed `pre_restore`.

## 6. Restore / duplicate handling: L1 only, no fabricated flight linkage

- Authorize target account on server, verify cryptographic signature and strict version dispatch, compute source event identity in trusted code, validate all source IDs and canonical event fingerprints; preview is advisory, not an authorization or concurrency safety gate.
- For v13 follow exact **approved A**, including cross-digest same-ID fail closed. For v14 signed-origin native event UIDs only compare when UID/proof/assignment provenance are valid. An absent, malformed or ambiguous historical UID **blocks dedupe**, never auto-assigns a source origin on import. All imported evidence remains separate, account-scoped and **unattached**; do not auto-map source `flight_id` to target `flights.id` even when numeric values coincide.
- In an atomic server-side DB operation, determine inserted/identical/conflicted imported rows using transaction-enforced uniqueness + full equality under concurrency. Do not `ON CONFLICT DO NOTHING` without strict equality, do not DELETE `flight_audit_log` rows, and do not use global `MAX(id)` as trigger cleanup. A fixed single-statement server-side SQL operation is a *candidate* compatible with Neon HTTP fixed-batch limitations, but remains unimplemented and UNVERIFIED.
- **Native v14 replay:** identical existing verified native UID+event fingerprint may be recognized as a locally pre-existing event **without writing any imported/native duplicate**; conflicting UID/content/origin must abort. When provenance is ambiguous, treat as unattached imported claim only if an owner-approved non-conflating representation exists; otherwise fail closed. Clone-split same numeric IDs cannot be merged. A replayed imported event retains its **original signed-v13 source digest and namespace** (or v14 source UID where proven), not the wrapping v14 file digest as a new identity.
- If native flight triggers run during restoring another flight, preserve every genuine audit insert. Do not attribute trigger's `actor_user_id=user_id` to an interactive pilot action. Certified revision/correction and shared participant record histories remain separately verified.
- All critical evidence checks must be inside the authoritative transaction or enforced by DB constraints. No outcome counts from preview/attempted inserts; report only actual committed inserts/verified idempotent matches, with safe generic conflict messages.
- Every unknown actor, backup version, origin identity, per-event proof, invalid owner or missing schema produces `UNAVAILABLE/NEEDS VERIFICATION` or an atomic conflict, not fabricated `CURRENT`/certification evidence.
