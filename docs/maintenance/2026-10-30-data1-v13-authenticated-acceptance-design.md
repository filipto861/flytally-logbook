## 3. Review findings requiring disposition BEFORE actual restore test

These are **source-observed gaps and unverified risks**, not production incident claims.

1. **Stored authenticity trust — HIGH, design decision.** `restoreStoredBackup` bypasses `portableBackupAuthenticity` by passing `"stored"` trust after owner-scoped retrieval; `loadStoredBackup` verifies JSON digest and DB-stored digest but not HMAC signature before protected-history restore. A corrupt or internally altered stored payload with a matching updated digest would not itself be rejected for absent/invalid server signature at this layer. Do **not** silently change this behavior: freeze owner decision on whether all stored v13 restores must also have valid HMAC, how old stored unsigned backups are handled, and safe failure messaging. Independently review the threat model, source contract, existing tests and migration/compatibility impact.
2. **Decompression bound — HIGH, availability risk.** `loadStoredBackup` calls `gunzipSync(Buffer.from(...))` without a per-read `maxOutputLength` or pre-decompression compressed-size validation. The 50 MiB limit protects creation, not necessarily malformed/legacy DB rows or decompressed expansion. Test very high-ratio *fabricated* gzip safely **in memory only** with bounded fixture; define agreed caps, memory budget, fail-closed errors and compatibility BEFORE any malicious payload enters SQL.
3. **Error disclosure — MEDIUM, verify.** `GET /api/backups/[id]` responds with `error.message` for exceptions mapped to 404. Error and ownership controls must be verified under malformed gzip, invalid signature, corrupted digest, absent row and other-user ID. Decide whether a single generic public error should replace detailed internal messages without weakening diagnostics.
4. **Schema writes on ostensibly read-only flows — HIGH operational boundary.** `getSession`, `loadStoredBackup`, `prepareExactAccountRestore` invoke `ensureDatabaseOptimizations`; `/data?view=recovery` calls `ensureDailyBackup`. `lib/db-optimization.ts` performs migration/shape enforcement and v21 fail-closed gates. Therefore opening a page or GET endpoint is **not proof of a database read-only transaction**. Tests require a *fully initialized, positively identified disposable* database and explicit isolation. Never point this code path at Logbook Shadow or production as a test convenience.
5. **Restore atomicity and concurrency — HIGH test requirement.** `executeExactAccountRestore` runs data SQL in a transaction, but preflight and `createStoredBackup("pre_restore")` are separate phases; a racing change after preview requires specific acceptance. PostgreSQL sequence operations and unrelated safety-backup writes must not be misreported as complete rollback of all side effects. Verify protected row invariants and row counts pre/post injected SQL failure and two-session contention. Do not claim a race defect without evidence.
6. **Cross-account / source provenance — HIGH test requirement.** Owner-scoped stored query, v13 profile/account binding, participant records, historical certified/voided evidence and HMAC must remain strictly scoped. Negative tests must prove a user B session cannot GET, preview, restore or infer user A's stored backup, including 404 response confidentiality and zero writes.

**Product decisions needed before implementation:** stored-v13 signature requirement/legacy treatment; explicit decompression/output cap; safe GET error contract; whether user-facing restore preview needs stronger DB-lock/re-read semantics. Independent read-only security/architecture reviewer (DeepSeek or Claude) recommended for these irreversible/evidence-critical boundaries; reviewer findings must be checked against exact source before owner decides.
