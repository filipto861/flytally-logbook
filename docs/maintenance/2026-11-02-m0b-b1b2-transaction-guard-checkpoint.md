## Implemented, deliberately narrow

- `lib/account-restore-v6.ts`: at the beginning of the existing fixed batch `sql.transaction(queries)`, stage a `LOCK TABLE` of `flights`, `fstd_sessions`, `flight_certified_revisions`, `fstd_certified_revisions`, `voided_certified_flights` in `SHARE ROW EXCLUSIVE` mode, **before user/settings/parent mutations**.
- Three **SQL-level** conditional abort guards (flight, FSTD and existing certified revision) check all incoming source parent identities against target **inside** that transaction: reject missing/foreign/incomplete parent identity, same numeric ID with contradictory date/natural-key/revision/hash, same natural identity under a different target ID, active vs voided certified tombstone, or same certified-child ID/revision conflicting with original hash/parent. Missing FSTD duration is not treated as 0. Guard error is deliberately fail-closed, but its raw PostgreSQL `22P02` type-cast diagnostic is **NOT an approved end-user error mapping** and must be redesigned before any public enablement. All inputs are passed through SQL tagged parameters, not manually interpolated.

## Critical outstanding safety constraints

1. Table-level `SHARE ROW EXCLUSIVE` locks can contend with ALL flight/FSTD writers, not just restore; performance, lock timeout and deadlock risk **UNMEASURED**. This is an experimental dormant guard, not an approved production restoration algorithm. Normal writers do not use consistent natural-key uniqueness/advisory locks; a duplicate can still arise **after** restore commits. Durable schema/account identity constraints or agreed cooperative writer lock strategy remain needed.
2. Only selected parent and certified revision fields are compared, not complete canonical row identity or all protected children. Shared participant/e-signature, GPS, expenses, independent user evidence, archive child relationships and authorisation are still outside transaction-bound proof; old generic `ON CONFLICT DO NOTHING` remains in those sections.
