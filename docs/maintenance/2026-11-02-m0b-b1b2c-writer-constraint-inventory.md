## Verified schema facts versus assumptions

- `lib/flight-dedup.ts` defines `flightFingerprint` using **user ID, date, registration, off-block, departure, arrival**, normalized by trim+uppercase.
- `lib/db-optimization.ts` migration 4 creates `idx_logbook_flights_restore_key ON flights(user_id,date,registration,off_block,departure,arrival)` as a regular **non-UNIQUE index**; it does NOT enforce natural flight identity across noncooperating writers.
- Migration 6 creates `idx_logbook_fstd_user_date ON fstd_sessions(user_id,session_date DESC,id DESC)`, also regular non-UNIQUE; FSTD protection trigger rejects certified changes, not natural-key duplicates.
- Existing specific UNIQUE constraints include flight `(id,user_id)`, source/participant relationship IDs and `(user_id,flight_id,revision_number)` certified-flight revision, FSTD analogous revision, and voided `(user_id,original_flight_id)`; none of these is equivalent to a universal cross-backup source-instance event ID.
- Source definition does NOT establish that two authentic real-world flights with same user/day/registration/off-block/route are universally forbidden. Blindly turning the heuristic tuple into `UNIQUE` would be an unapproved product rule and could fail on historical duplicates. Data inventory and owner product decision are needed.
- The actual Neon HTTP driver is used via `lib/db.ts` `neon(DATABASE_URL)` and fixed `sql.transaction([...])`. The local PG executor is separate. The driver documents noninteractive HTTP batches, but this exact staged lock/rollback strategy has **not** been exercised against an isolated Neon HTTP endpoint. Neon parity UNKNOWN.

## B1b.2c minimal, fail-closed design direction (proposal only)

1. **Separate identities:** immutable source-instance ID + event ID for v14 provenance, storage row PK, and human-readable flight/FSTD fingerprint. Avoid treating fingerprint or numeric DB ID as a proven cross-instance identity; a key collision is a conflict, not auto-merge.
2. **Preserve Create/QuickAdd/Shared current behavior** while documenting their actual advisory lock key. For scoped restoration of an event known not to exist, acquire matching advisory locks, but ONLY claim race-freedom after **Edit/Trash/FSTD/void/certification** paths are reconciled or DB uniqueness is enforced. Do not add a restore-only lock and call it safe.
3. **No new schema or irreversible change without approval.** First define additive v22 proposal and historical duplicate/migration read-only checks, exact target DB separation and rollback, provenance/issuer model with B2 append-only imported audit and coherent signed v14 backup. Until then `UNAVAILABLE` / M0-A block full restore. Normal Trash recovery remains available.
4. **Acceptance:** reproduce two-session ordinary Create vs Restore, Edit modifying natural key vs Restore, FSTD Create/Edit vs Restore, Trash/void parent and protected-child vs Restore, shared participant source evidence; prove no cross-user writer contention, original native audit unchanged, no certification fabrication and fail-closed on missing/mismatched source identity, including actual Neon HTTP fixed-batch behavior on explicitly isolated test resources.
