## 2. Explicit decision to request: M0-A immediate fail-closed server containment

**Recommended owner approval: temporarily DISABLE execution of ALL full-account backup restores**, covering both stored and uploaded `v4+` inputs, **without disabling backups, backup readback, file verification or preview**. This is a temporary trade-off: recovering a whole account from backup becomes unavailable until a separately reviewed safe importer is implemented.

Minimum proposed implementation after separate owner approval:

1. In the shared `app/(protected)/export/actions.ts` `restoreParsedBackup` flow, BEFORE `prepareExactAccountRestore`, `buildPreview`, any `pre_restore` creation or legacy mutations, branch on `intent==="restore"` and return a bounded generic error **without calling any mutating backend**; allow `intent==="preview"` to keep existing behavior (it may perform existing schema-preflight; do not advertise preview as guaranteed read-only). Malformed/unknown intent must never bypass gate into a write path. Apply the same explicit guard at both exported actions before any unnecessary stored/file prepare work when feasible, without bypassing auth or version checks.
2. **Independent second barrier:** put fail-closed execution guard at the first line of exported `executeExactAccountRestore` in `lib/account-restore-v6.ts` *before* `ensureV16xSchema`, currency checks and native audit `MAX`; this ensures a future second server caller or forged form cannot bypass action-only controls. `restoreLegacy` is currently a module-local function, but protect its invocation by the shared action guard and test its inaccessibility. No bypassing environment flag or silent fallback. Hard guard removal is a separate risk/owner decision.
3. Minimal explicit UI containment (NO new styling library/brand/motion): file/stored backup sections show visible message “Full account restore is temporarily unavailable while we protect your flight history. Backups can still be created, checked and downloaded.” Hide or disable only the full-account **RESTORE** confirmation action; preserve filename, metadata, Check/preview, Download and Create backup. Use existing error/alert semantics, keyboard focus and accessible status. **Motion: NONE.** Do not label a disabled backup restore as “safe / ready to execute” or present a success message. User-facing text should not expose raw SQL, flight/GPS or private internal IDs.
4. Protect both saved-backup and uploaded backup action paths **on the server** even if the UI is bypassed, and preserve authorization. `restoreDeletedFlight` / individual Trash records remain unchanged **unless independent investigation finds the identical bug**; don't silently disable unrelated pilot workflows.
5. Do not delete the original unsafe SQL in M0-A and then claim it has been permanently repaired: it remains a **latent technical debt requiring M0-B/V13-I**. It must be provably unreachable on all full-account restore write paths while the guard is active; track that condition with durable regression tests.

**Alternative (not recommended as immediate containment):** try to keep full restore writable by only removing the native audit DELETE and imported native INSERT. This can silently drop signed historical source audit evidence while appearing successful. Correct V13-I preservation requires new immutable ledger + all-path v14-complete backup/restore, key policy, ownership constraints and production migration; too broad for a fast production safety patch. No silent “empty audit” exceptions.
