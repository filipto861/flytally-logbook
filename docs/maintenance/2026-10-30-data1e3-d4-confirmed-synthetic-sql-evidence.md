## 2. Mechanism checked independently against frozen code

**Source:** [\`lib/account-restore-v6.ts\` at exact owner-tested SHA](https://github.com/filipto861/flytally-logbook/blob/cf2332d3814fd5f97096608680dffdb1d457c5df/lib/account-restore-v6.ts).

1. \`prepareExactAccountRestore()\` lines **119–215** checks current account data and computes a \`plan.addRows\` **before execution**. The plan is not automatically revalidated in a subsequent transaction; external changes can make it stale.
2. \`executeExactAccountRestore()\` lines **220–225** revalidates input structures but starts by reading \`MAX(flight_audit_log.id)\` into \`auditFloor\` **outside** the main \`sql.transaction(queries)\` at line **282**.
3. Lines **233–235** stage flight rows and \`INSERT ... ON CONFLICT DO NOTHING\`, then \`UPDATE flights\` by user+ID using all \`plan.addRows.flights\`, **regardless of which INSERTs returned a new row**. Lines **242–244** repeat the pattern for \`fstd_sessions\`. If another record with the same ID exists by execution time, its protected/certification fields can be overwritten. A source preview and even a pre-execution no-conflict SELECT cannot alone prevent a race.
4. Line **266** deletes rows from \`flight_audit_log\` where \`user_id\`, \`id > auditFloor\` and \`flight_id\` in planned new flights. This is a broad ID-based deletion that does **not** establish that the deleted audit row was generated by the present restore. An independently appended event after reading \`auditFloor\` can satisfy this predicate.
5. Line **283** returns the sum of planned preview additions, **not actual database INSERT successes**; F8 reported counts can be wrong under a collision.
6. \`sql.transaction(queries)\` at line **282** is atomic for the included statements when successful, but does not retroactively protect the earlier preview or \`auditFloor\`; the separately committed pre-restore safety backup remains a distinct side effect in \`app/(protected)/export/actions.ts\`.
7. **The executed risk test** [\`tooling/data1e3-d4-source-sql-risk-probe.mjs\`](https://github.com/filipto861/flytally-logbook/blob/cf2332d3814fd5f97096608680dffdb1d457c5df/tooling/data1e3-d4-source-sql-risk-probe.mjs) extracts and runs the **actual source SQL blocks** in its own synthetic schema. It inserts conflicting flight/FSTD rows after a simulated preview and inserts a later independent audit row after \`auditFloor\`. The three observed FAIL booleans directly support these SQL mechanisms. **It is not two physically concurrent sessions, does not run the exact production schema/triggers, and does not exercise the full Next.js restore action.**
