### Corrections/qualifications to independent report

1. **v12 is version-sensitive.** The full `lib/backup-authenticity.ts:15-19` treats **missing signatures as INVALID for version >=12** and returns `verified` only after checking the signature payload. However, `app/(protected)/export/actions.ts:84-107` enforces mandatory signed status on portable/stored restores only for version **>=13**; stored older backups use `trustedSharedState:true` and an `authenticity:"stored"` label. Do not misstate v12 as universally unsigned or universally signature-required on restore. This is a trust-policy audit item, not a claim of a newly exploited flaw.
2. **DeepSeek's F-01 recommendation has a trade-off**: selecting a `UNIQUE(destination_user_id,source_user_id,source_audit_id)` canonical identity and treating a second signed snapshot with equal content as the same event risks collapsing genuinely independent events from cloned databases. Under the already-frozen preservation policy the **safest default is to BLOCK ambiguous cross-snapshot overlaps even when content is equal**, until stronger provenance is available; product usability cost is explicit.
3. **Source-to-target link:** no ID-based automatic association. A link must use independently checked account ownership, exact parent identity and immutable evidence, and must remain an auxiliary revocable association, not edit the archive or native event.
4. **Raw lexical bytes:** current JSON parsing hashes serialized parsed payload. Raw original JSON substrings are not automatically equivalent to what was signed. A future evidence-byte scheme requires an explicit parsed representation/version or a retained exact verified canonical signed payload.
5. **Confidence:** source facts are verified at `6fd5597...`; severity is a reviewer prioritization, not a test outcome. No A2 new schema or runtime was run, so P0/P1 are **design blockers / old-code confirmed conditions**, not newly measured production exploitability.
