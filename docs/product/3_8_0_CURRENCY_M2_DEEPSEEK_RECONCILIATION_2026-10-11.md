## Verified source points

- `lib/migration-plan.ts:1–24`: DB schema version 20; v21 unregistered. `lib/db-optimization.ts:849–874`: `migrateDatabase` iterates pending versions, automatically executes queries in `sql.transaction`; registering v21 and releasing runtime with the correct DB access could execute it on init. - `lib/db-optimization.ts:792–845`: v20 flight protection relies on `to_jsonb(OLD)` comparisons in certified correction and void workflows; `lib/certification-integrity.ts` v8 doesn't include monetary values, but certification hash scope does NOT waive database immutability. Never UPDATE old certified rows for currency classification.
- `lib/account-restore-v6.ts:193–204`: backup restore is name-based JSON data to `NULL::flights/rates/aircraft/flight_expenses` via `json_populate_record`, not explicit manual projection; absent new keys should become NULL but signing and trigger behavior need actual PostgreSQL tests.
- `lib/flight-trash.ts:12`: restored flights use an explicit INSERT column projection with legacy numeric price and expenses; a later writer must preserve monetary metadata. Earlier legacy trash snapshots without money metadata must stay unresolved, not default to CZK.
- `lib/flight-expenses.ts:9–15,26–27,33–40`: old parser uses `*100` and formatter `/100` **for all codes**, accepting syntactic `[A-Z]{3}` only; `expenseTotals` incorrectly adds a derived aircraft cost as CZK. Historical JPY/KWD entries therefore have **legacy two-decimal storage encoding**, not ISO-native minor-unit encoding. This is a **representation compatibility issue**; the reviewer claim that their amount was “wrong” is too strong absent the user's original entered display value. Neon Shadow currently has zero expense rows; backups may not.
- `app/(protected)/database/actions.ts:28–31,57` and `components/aircraft-manager.tsx:56,65–66`: wet/dry amounts currently appear together on **one dated rate record and one form**; UI labels both CZK/h, no separate currency selector. `app/(protected)/connections/aircraft-share-actions.ts:47–48,95`: shared rate wet/dry are transferred together without currency. Single currency per rate row is the smallest backward-compatible technical candidate. A future wet/dry-mixed-denomination feature requires an explicit contract and separate UI; **do not silently accept distinct currencies in one row now**.
- `app/(protected)/flights/actions.ts:92,107,172,224,249`: `COALESCE` numeric resolved price is detached from currency/source. M3 must return an atomic source tuple and handle all Create/Edit/GPS/Share paths.

## M2-A-0 narrow implementation choice

- The isolated code artifacts in scope are [unregistered offline SQL draft PR #322](https://github.com/filipto861/flytally-logbook/pull/322): 12 nullable money metadata fields across `rates`, `aircraft`, `flights`, `flight_expenses`; four explicitly named shape/encoding `CHECK` constraints; six new focused PostgreSQL integration cases under `tests/integration/` and a [Docker/Node24 Windows runner](3_8_0_CURRENCY_M2A0_LOCAL_POSTGRES_HANDOFF.md). The new tests are authored but **NOT EXECUTED**. It does not modify `lib/migration-plan.ts`, `lib/db-optimization.ts`, default settings, live flight/rate writers, backup/restore or protected history. No remote SQL.
- Technical points **not frozen by merely drafting SQL:** new numeric precision/range, sole source-of-truth semantics, optional source-rate id on flight snapshot, exact billing round rule, wet/dry mixed currency beyond same-record contract, typed read-model state derivation, D2 attestation table and v13 backup compatibility after new currency writes.
- **PostgreSQL three-valued-logic trap:** a `CHECK` evaluating to NULL passes. The draft was corrected to require explicit `IS NOT NULL` for all required fields of a known-price tuple and `COALESCE(...,FALSE)` for expense encoding; true source-level PG rejection still needs local PG tests.
