## E1.3 requested outcome

For GPS-imported flights, suggest Day vs Night landing counts from the **actual detected landing events** using EASA/SERA civil twilight, without turning the suggestion into aircraft/regulatory authority and without overwriting pilot edits.

Initial scope remains GPS-only.

## Authoritative rule / source hierarchy

Primary regulatory rule:
- Commission Implementing Regulation (EU) No 923/2012 (SERA), Article 2(97): night is between end of evening civil twilight and beginning of morning civil twilight; the centre of the Sun's disc is 6° below the horizon at the civil-twilight boundary.
- Current consolidated EUR-Lex text: CELEX 02012R0923.

Astronomical definition:
- U.S. Naval Observatory defines civil twilight computationally at **geometric solar-centre altitude -6°** / zenith distance 96°.
- No sunrise/sunset 0.833° atmospheric-refraction / solar-radius correction belongs in this civil-twilight threshold.

Candidate calculation basis:
- NOAA solar-position equations based on Jean Meeus, using Julian century / geometric solar coordinates and true solar time.
- Use **geometric** solar-centre altitude; do not apply NOAA atmospheric-refraction correction.
- NOAA states its approximations are very good for 1800–2100; proposal is to fail closed outside that supported date range.

Relevant public references:
- https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:02012R0923-20250501
- https://aa.usno.navy.mil/faq/RST_defs
- https://aa.usno.navy.mil/data/api.html
- https://gml.noaa.gov/grad/solcalc/solareqns.PDF
- https://gml.noaa.gov/grad/solcalc/calcdetails.html

- user must check “I reviewed this flight” before Save;
- server already validates Day + Night == reviewed total;
- current aircraft change effect clears flight-specific regulatory evidence.

`lib/track-time.ts`
- explicit `Z` timestamps are UTC;
- explicit numeric offsets are accepted and normalize to an exact UTC instant;
- timezone-less timestamps are classified `ambiguous` and must fail closed.

### Strongest landing-event source

For each split flight:
1. every detected T&G uses `part[touch.index]`;
2. final landing uses `part[flightEnvelope(part).landingIndex]`;
3. event classification uses that point's **own timestamp + own lat/lon**;
4. do not substitute `flightEnvelope().landingUtc` fallback when the exact landing point has no timestamp;
5. if any required event is unclassifiable, the aggregate Day/Night suggestion is unavailable.

Arrival-aerodrome coordinates are not needed for GPS E1.3 and should not override event coordinates.

## Draft implementation contract

### Pure classifier

New pure helper, no DB/browser dependency:

```ts
type CivilTwilightClass = "DAY" | "NIGHT" | "UNAVAILABLE";

classifyCivilTwilightEvent({
  timestamp,
  lat,
  lon,
}): CivilTwilightClass
```

Input rules:
- timestamp must contain explicit `Z` or numeric UTC offset;
- parsed instant must be finite;
- supported year 1800–2100;
- latitude finite in [-90,90];
- longitude finite in [-180,180];
- non-finite calculation => UNAVAILABLE.

Classification:
- geometric solar-centre altitude >= -6° => DAY;
- geometric solar-centre altitude < -6° => NIGHT;
- no arbitrary epsilon;
- polar day/twilight/night is classified at the actual timestamp, not treated as UNKNOWN merely because no twilight crossing occurs.

### Event aggregate

A second pure/helper layer should:
- derive T&G + final landing event points from one split part;
- classify every event;
- return `AVAILABLE {day,night,total}` only if every event classified;
- otherwise return `UNAVAILABLE`;
- assert `day + night === detected landing total`.

### Applicability

Automatic prefill should initially apply only when:
- GPS source review requires `landingMode === "DAY_NIGHT"`; and
- selected aircraft/profile evidence uses the EASA/SERA path.

Do **not** silently apply this SERA rule to unrelated jurisdiction-specific logbooks. Other contexts remain manual until a first-class rule source exists.

### Sticky user override

Current `Review` state needs explicit provenance/state, not heuristic value comparison.

Proposed states:
- `UNSET`
- `SUGGESTED`
- `MANUAL`

Rules:
- new track or changed split => reconstruct part reviews and recalculate suggestion;
- initial applicable EASA DAY_NIGHT review may prefill available suggestion;
- editing either Day or Night field changes provenance to MANUAL;
- unrelated state changes (airport auto-detection, Role/Crew, billing, Operation, etc.) must not overwrite MANUAL values;
- changing reviewed total while values are still SUGGESTED should invalidate/clear the automatic split rather than invent a distribution;
- changing source track/split may replace MANUAL because source-event identity changed and the entire part review is already reset;
- changing applicability from DAY_NIGHT to TOTAL/non-applicable must fail closed rather than reinterpret the same numeric field with different semantics.

### UI copy / provenance

For available EASA suggestion:
- label as **EASA/SERA civil-twilight suggestion**;
- provenance: **GPS event time/location**;
- pilot can edit before review/save.

For unavailable suggestion:
- explain that one or more landing events lacks usable explicit timestamp/location;
- keep manual Day/Night inputs;
- no inferred airport/timezone replacement.

No new certification payload fields are proposed; persisted evidence remains the pilot-reviewed Day/Night counts already in the canonical flight model.
