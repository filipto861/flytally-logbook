## Additional source-backed implementation risks missed or under-specified by reviewer

1. **Certified flight mutation ≠ certification hash scope.** `lib/certification-integrity.ts` v8 payload does not include rates/prices, but `lib/db-optimization.ts` function `logbook_protect_locked_flight()` forbids UPDATE/DELETE on certified flights. `lib/flight-certification.ts` certifies and locks rows. Therefore "currency outside hash" does **not** authorize UPDATE of `flights.currency_code` on a certified row. For historical confirmation, explore separate **owner-scoped append-only attestation ledger**, keyed to stable flight/rate identity and monetary value evidence, with revocation and independently verified read-time resolution. Never rewrite protected certified/voided JSON snapshots.
2. **Trash restore is explicit-column, not automatic.** `lib/flight-trash.ts` `restoreDeletedFlightRecord` reconstructs `price_per_hour` but no future currency/exact-money fields. It must be updated and tested if columns are added. Restore handling for known, unknown and invalid money must be explicit.
3. **Rate/aircraft import/upsert overwrite.** `app/(protected)/database/actions.ts` and `app/(protected)/connections/aircraft-share-actions.ts` perform upsert by rate date and may overwrite an existing rate. Currency provenance, `undefined` preserve / explicit null clear / value set, and conflict presentation must be part of reviewed M3/M5 semantics. Imported source rates must never be assumed to share recipient account currency.
4. **Fallback `COALESCE(r.price_per_hour,a.default_price_per_hour)` loses provenance.** `app/(protected)/flights/actions.ts` `resolvedPrice` returns only the number; new rate resolution must select amount **and the matching row's currency as one atomic source choice** rather than separately coalescing amount/currency. GPS `priceCache` currently holds numbers and requires the same fix.
5. **Current numerical aggregation may silently include unknown.** `lib/data/dashboard.ts`, `lib/data/pilot-insights.ts`, and `lib/data/flights-fast.ts` require grouped-by-denomination redesign, while `lib/billing.ts` currently maps malformed/missing price inputs into numerical 0. Ensure domain status is preserved until display.
6. **Reversibility is not `DROP COLUMN` after new writes.** Dropping new denomination/exact-value columns after users start recording them destroys new provenance. Rollback after production writes must be a compatibility-code rollback (retaining additive columns), or a separately reviewed lossless recovery/dual-write plan; never assume schema-drop safe.
7. **No unconditional `UNKNOWN` string in DB.** A nullable persisted code can mean unresolved denomination, but at the API boundary a typed status is preferable to conflate-free serialization (e.g. `{state:"unknown_currency",amount:...}`). A code `"UNKNOWN"` is not ISO currency; it must not be persisted as a valid three-letter currency value.

## Owner decision D4 — APPROVED (11 October 2026)

**Owner statement:** Support all currencies, not only the initial six, in FlyTally 3.8.0. This supersedes DeepSeek's D4 narrow-scope recommendation. This is a **product scope decision**, not permission to assume a particular monetary database representation, numeric precision conversion, historical attestation or FX functionality.

**Frozen D4 outcome / acceptance contract:**

- **Coverage:** All **active ISO 4217 currencies representing monetary tender** for which the authoritative registry provides an explicit minor-unit exponent; no artificial short allowlist (CZK/EUR/USD/GBP/CHF/PLN are examples and may be prominent in UI, not the full supported set). Include currency codes beginning with **X** when they denote real currencies (e.g. XAF, XOF, XPF); don't reject by prefix.
- **Source of truth:** ISO 4217 Maintenance Agency **SIX**, official [currency lists/updates](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html), especially *List One: Current Currency & Funds* and relevant amendments. **Separate monetary currencies** from fund/accounting units, metals (e.g. XAU), test codes (XTS), no-currency (XXX), and entries whose minor-unit field is `N.A.`. This separation requires reviewed, reproducible classification; do not fabricate or silently accept every three-letter code as a monetary currency.
- **Precisions:** Do not assume two decimals; support **all published ISO minor-unit exponents** for eligible currencies (examples: JPY 0, EUR 2, KWD 3). Build a single shared, versioned, source-backed currency registry with code/name/exponent/status/reference revision, used by server parsing, DB/write validation, expense form, aircraft rates, flight snapshots, reports, and formatting.
- **Historical preservation:** A code that later ceases to be current does **not** invalidate or re-denominate existing historical transactions. Retain the original code and the precision applicable at recording (store precision/provenance or bind to an immutable registry version; exact physical schema remains M1). New entry of withdrawn/historical codes is **not automatically authorized** by D4. Reviewed historical data and older v13 backups remain readable without inventing missing denomination.
- **Arithmetic:** Parse and compute in exact decimal/scaled representation and apply a defined rounding policy at the proper boundary; **never** mix JPY/KWD with `/100` logic or convert amounts merely because Settings changes. Never infer an FX rate. No silent coercion of malformed or missing currency to CZK/zero.
- **UX:** Compact searchable selector with major/common currencies at top and **all** other eligible currencies searchable by code/name, avoiding a cluttered form; the selected currency remains explicit per persisted monetary record.
- **Offline/runtime authority:** The shipped app uses a repository-pinned reviewed registry, not runtime third-party fetching. Registry updates have explicit source date/effectivity, diff, tests and deploy; currencies must not silently mutate previously persisted amounts if reference metadata changes.
- **Evidence gate:** Full ISO list ingestion and its currency/funds classification have **NOT RUN**. Before implementation, obtain and pin the actual authoritative List One release, verify classifications/exponents (including special codes and codes altered in recent amendments), test `0/2/3` and any other supported exponent, strict rejected codes, historical restore and future metadata changes. The official SIX page confirms that List One includes **currencies AND funds**, and separately publishes List Two and historical List Three; D4 approval does not override that evidence requirement.

**Explicit exclusions:** no crypto/private non-ISO units, no funds/metals/test codes automatically placed in the monetary input picker, no automatic exchange-rate service, no retroactive conversion. Future requests for additional denominations require separate product scope.
