## Reconstructed present workflow

- New route `app/(protected)/flights/new/page.tsx` loads aircraft profile options, Manual defaults, calendar, connected pilots and recent flight insights; `FlightEntryWorkspace` switches two mounted-but-one-hidden components, maintaining each mode's React state. It also hosts Quick Aircraft in a focus-managed dialog.
- Manual `components/flight-form.tsx` is **also used by Flight Detail editing**. Initial primary card contains Date, Registration, Role and context-dependent instructor/crew, Departure/Arrival, four time fields and live BLOCK/AIR. Additional `details` sections: Experience, Additional crew, Aircraft context, Optional details (Training, Night/IFR, Costs, Notes); Review & finish, missing-required jump buttons and Save draft / Save & certify. Conditional source branches contain 42 `<label>` tags, NOT 42 simultaneous visible fields.
- GPS `components/kml-import-form.tsx` separately owns upload KML/GPX/CSV, track-quality/time-basis warnings, optional or automatically opened map/replay and split editor, common Aircraft/Role/Crew context and optional Costs, then `parts.map(...)` produces full flight review cards with part-level date, airports, landing/takeoff evidence, role overrides, times and notes; Review & finish (one part), readiness and explicit save. Parser/part source quality, day/night suggestions and server-side GPS integrity remain their own authority. Conditional source branches contain 40 `<label>` tags, NOT 40 simultaneous visible fields; multiple parts can produce repeated cards.
- `components/intelligent-flight-entry-panel.tsx` portals historical checks into Manual labels, plus optional route suggestion and fallback attention panel; suggestions are explicit actions, not silently applied.
- CSS ownership is layered: `app/globals.css`, `app/v157-flight-entry-workflow.css`, `v158`, `v159`, `v160`, `v161`, `v300-u4-flight-workflow.css`, with `app/ui-system.css` imported last in `app/layout.tsx`. Existing effective mobile `entry-choice` rule must be verified against **final cascade**, not judged from an earlier `globals.css` declaration.

## Proposed N3 interaction model (no implementation approved)

**Entry-level:** "New flight" → segmented Manual / GPS selection, one shared status summary showing source, aircraft and what is still needed, then a focused work area and clear completion action. Retain state when switching and confirm loss of unsaved work when truly necessary. Accessibility semantics and focus order remain explicit. Motion choice **NONE** (allow only existing short feedback transitions).

**Manual primary view:** Aircraft + Date + Pilot role; Departure / Arrival + OFF/Takeoff/Landing/ON; relevant landing/experience evidence visible where required; compact live BLOCK/AIR and concise review/save. Advanced Aircraft Context, Crew, Training, Night/IFR, Costs and Notes stay discoverable and expand automatically where a validated requirement/error demands it. Required fields still vary by aircraft/evidence; no invented uniform "mandatory route" rule.

**GPS primary view:** (1) Upload one track and display parse/source quality; (2) common aircraft/role plus required operation context; (3) clear per-flight review/status and map/split tools exposed when justified; (4) explicit per-flight evidence approval, summary and save. No automatic acceptance or certification of inferred flight/landing/time/aircraft facts. Single GPS flight can Save draft or Save & certify; multi-flight import remains drafts only unless separately decided.

**Layout:** desktop generous primary reading column plus optional compact readiness rail only if it improves scanning; iPad and phone stack into one column, with no sticky control covering fields or iOS keyboard. Keep light/dark and actual present FlyTally palette; no new fonts, packages, glass effects, animation framework or new interaction library. Existing `pending-action-button` and shared spacing/radius tokens take precedence over novel components.
